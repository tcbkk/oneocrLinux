# 安装 ID 识别对比：Windows 版 vs Linux 版

测试对象：10 张 Windows / Office 电话激活界面的截图与手机翻拍照片，
目标是从中读出「安装 ID」（9 组 × 7 位数字）。

* Windows 版 = 原 `oneocr.dll` + `onnxruntime.dll`（x64，本机）
* Linux 版 = `oneocr_linux`（纯 ONNX），本机 Windows 与服务器 Ubuntu 各跑一次

## 关键修复：倾斜框的透视裁剪

第一版 Linux 实现在这 10 张上只有 6 张成功，第 3 张（手机翻拍）读成
`Sar per Cine2105 c5to2 ...` 这类垃圾。

原因不是分辨率或预处理，而是**框的形状**：原版 `GetOcrLineBoundingBox` 返回的是
**四点多边形**，第 3 张的安装 ID 行是

```
(60,680) (564,732) (562,751) (59,694)      // 上边倾斜 ≈5.9°
```

按轴对齐矩形 `(60,680)-(564,732)` 裁剪，会把倾斜的行切歪、混入上下行内容。
改成用四点做透视变换拉直后，识别结果一次性变为完全正确：

```
252**** 285**** 201**** 428**** 754**** 333**** 553**** 706**** 542****
```

Linux 版现在的做法：对每个连通域内的 hot cell 点集做 PCA，拟合文本行方向，
输出四点旋转框，再用 `PIL.Image.transform(..., Image.QUAD, ...)` 裁剪。

这也解释了原项目 `ImagePreprocess.cs` 里那段注释——它对边缘锐度敏感，
但更根本的是框必须先拉直。

## 三个未通过的样本

* **#4（683×46）**：Windows 版直接返回 **0 行**（`RunOcrPipeline` 成功但没有 line），
  原引擎对小图有尺寸下限。Linux 版把短边补到 32 的倍数后能正常识别，
  所以这一张是 Linux 版**独有**的能力。
* **#2 / #8 / #10（阿拉伯语界面）**：安装 ID 是 9 个独立小格（RTL 网格），
  不是一行连续文本。两版都把它们切成单字符碎片（`9A`、`7`、`E`…），
  无法拼回 7 位数字组。属于已声明的「只支持横排文本行」限制，
  需要网格/竖排版面分析，Windows 版同样没有通过。

## 结论

* 对**横排、清晰**的安装 ID 截图，两个版本输出完全一致，Linux 版可无缝替代；
* Linux 版在手机翻拍（倾斜）场景下，靠四点透视裁剪已达到与 Windows 相同的结果；
* 剩余差距只在网格/竖排版面，属于后处理能力而非模型能力。
